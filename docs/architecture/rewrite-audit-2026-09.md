Phase 1 规划时又核实了两个正在出错的问题，放在 Phase 1 的预备发布里修：

- **"今天"的汇率被错存。** `parseProviderRates` 丢掉服务商返回的日期，一律存在请求的日期下（`exchange-rates.ts:57`）。在 ECB 当天发布之前查询"今天"，前一天的汇率就被永久存成今天的。过去的日期不受影响：周六存周五的汇率，本来就是那一天适用的汇率。
- **详情页改日期后保存必定失败。** `f4983bd4` 把服务端字段改名为 `documentDate`，客户端的待保存字段仍然叫 `entryDate`，而 strict schema 会拒绝多余的 key。两个类型都有 `title`，所以 tsc 没有报错。

另一个问题：**CI 不拦部署**。推送到 `main` 后，Vercel 立刻迁移并部署，与 CI 并行跑（已核实）。目前靠提交前在本地跑 `npm run check` 兜底，改造放在 J 里。

## 二、从头写会推翻的决定

按收益从高到低排列。

### A. 日期挂在票据上，而不是条目上（L，不做）

- **现状**：`ledger_entries` 表没有日期列（已核实），日期只存在 `source_documents.document_date / effective_date` 上。同一张票据里的条目要落在不同的日期，只能靠三个补丁：
  - **拆分**（`split.ts`）：新建文档，复制文件关联，再把条目搬过去。
  - **日期整理**（`date-organization.ts`）：按 AI 给出的 `date_hint` 把一个文档拆成 N 份。
  - **日期影响预览**（`get-batch-entry-date-impact.ts`）：因为改一条的日期会连带改动同文档的其他条目。
- **来历**：条目原本有日期，`1b74967f`（2026-02）把它移到了文档上。之后的拆分（`b4de3443`，2026-08）和日期整理（`04d9dc79`，2026-09）都是在补这个空缺。
- **重写**：`entries.date NOT NULL`，默认取票据日期，AI 的日期提示直接写进去。删掉拆分和日期整理，流式列表在视图层按日期分组。
- **结论（2026-09-25）**：不做。多日期输入并不常见，为它改约 53 个文件不划算。日期留在票据上，拆分和日期整理保留。
- **代价**：约 53 个文件引用了文档日期，统计和游标排序要一起改。能删掉约 1.2k 行代码和 2.2k 行测试。回填用 `entry.date = document.effective_date`。

### B. 折算金额存进库里（Phase 1，M–L，已做）

- **现状**：条目上存了 `converted_amount` 和 `exchange_rate`。为了让它们保持同步，配套了一整套东西：
  - 汇率重算任务表和 runner，约 450 行。
  - 8 处主币种比较（`writes.ts`、`updates.ts`、`entry-commands.ts` 各 2 处，`split.ts`、`date-organization.ts` 各 1 处）。审计时写的"33 处账本锁"不准确：账本锁还在保护分类和分账的存在性，B 只删主币种比较，不删锁。
  - 修改主币种之前要预取所有日期的汇率。
  - 折算公式有 TypeScript 和 SQL 两份实现。
  - 客户端还有第二条实时折算路径（`useConvertedAmount`）。
- **问题**：汇率按日期缓存，而且永远不会更新，所以存下来的只是派生缓存。新文档都有日期，重算实际上只作用于遗留的无日期文档，而这些文档的折算额会随着"最新汇率"每天悄悄变化。
- **潜在 bug**：`parseProviderRates` 用请求的日期覆盖了服务商返回的日期（`exchange-rates.ts:57`，已核实）。如果在 ECB 当天的汇率发布之前请求"今天"，前一天的汇率就会被永久存成今天的。
- **重写**：只存金额和币种，读取时 join 规范化后的汇率表来折算。主币种变更时不需要重算，也不需要加锁。
- **小步先行**：给无日期文档回填日期，然后删掉重算任务。
- **结果**：条目只存金额和币种。读取时用 SQL 函数 `convert_amount` 按票据日期折算，汇率存在 `exchange_rates`，每个自然日一行。缺汇率时显示为未折算，由维护流程补齐。重算任务、存量折算值和 8 处主币种比较都已删除；账本锁保留。

### C. 版本号与过期检测协议（Phase 1，L，已做）

- **来历**：`ac05d0aa`（离线优先）为离线队列回放引入了这套协议。离线模式在 `515ffcb5` 被删除，但 `aa9d9d8d` 反而把它推广到了所有写入路径。现在有 46 个源文件、42 个测试文件在用它。
- **现在还在防的**：后台写入（汇率重算、分类）会把版本号 +1；另外就是两个人或多个标签页同时编辑。
- **重写**：条目改为字段级 PATCH，只在详情页"整体保存"时检查 `updated_at`；后台写入不再改动用户可见的版本号。两个人确实会同时使用，所以整体保存这一处的检查要保留。
- **结果**：只有整体保存还带 `expectedVersion`，而且只写它补丁的字段。检查仍用整数 `version`，没有改用 `updated_at`：两者的时间精度不一致（ms 与 µs），比较会出错。`version` 只在标题、日期或条目变化时 +1。分类任务改为逐条比较并交换，不再动版本号。其他命令改为各自需要的前置条件。

### D. revision、outbox 与条目：三份重复的状态（Phase 1，L，已做）

- **现状**：
  - 文档上同时有 active 和 latest 两个 revision 指针。
  - `processing_outbox` 与 revision 一一对应，两边都有状态字段。`processing/jobs.ts:87-125` 专门写了一段 CTE 来修正两者之间的偏差。
  - 条目上的 revision 外键在 22 个文件中被引用，而相关的 join 条件永远为真，因为替换条目时会软删整组旧条目。
  - 只有 revision 已经完成时才会走 "residual" 完成路径，这是已经合并掉的 attempts 表留下的。
  - 调度恢复时就把尝试次数 +1，而不是在真正认领时才计数。
  - 恢复流程每次轮询都会锁账本行。
- **重写**：拆成 `receipts`、`receipt_files`、`extraction_attempts` 三张表，其中 attempts 表本身就是任务队列。
- **小步先行（S）**：删掉 residual 路径，把计数挪到认领时，去掉恢复流程对账本的锁。
- **结果**：表名没改，概念与表的对应关系见总纲第 2 节。
  - 提取尝试本身就是任务队列：认领、续租、计数都在 revision 上。
  - `processing_outbox`、`revision_files`、active 指针、条目上的 revision 列都已删除（迁移 0008）。
  - 条目和当前输入只属于票据，文件放在 `source_document_files`。
  - 手动 revision 不再创建，存量的 264 条已经删除。

### E. 后台租约：五套实现，规则各不相同（Phase 2，M，待做）

- **现状**：processing、分类文档、汇率任务、对象清理、幂等记录各自手写了一套租约。退避规则有 5 种，错误码方案有 4 种，判断过期时有的用 `<=`、有的用 `<`，完成时有的检查过期、有的不检查，有的用数据库时钟、有的用应用时钟。
  - 汇率重算是纯数据库事务，用 `FOR UPDATE SKIP LOCKED` 就够了。
  - 对象清理本身是幂等的。
  - 这两处的租约其实什么也没保护。
- **没有 cron**：维护只有在上传时顺带执行（`scheduleRequestMaintenance`）。
- **错误分类失效**：`processing/execute-job.ts` 的 `toFailureCode` 匹配大写错误码，而 AI 客户端抛出的是小写的 `ai_rate_limited` 等，`parser.ts` 还会把它包进 `cause`。所以限流和配置错误从来没有被单独识别过。
- **API v1 放弃上传会话时**，会为从未写入过的 `temporary/` key 排清理任务，真正写入的永久对象反而没人清理。
- **重写**：只有提取和分类两个流程需要租约，二者共用一个租约帮手；再加一个每日 cron 做兜底清扫。

### F. 上传用了四张表（Phase 2，M–L，待做）

- **现状**：`upload_sessions`、`upload_session_files`、`stored_files`、`object_cleanup_jobs`，外加大约 1,000 行代码。
  - API v1 收到的图片已经在服务器内存里，却仍然要走一遍"代理上传会话"（`prepare-inline-images.ts`）。
  - `stored_files.deleted_at` 从来没有被写入过。
- **重写**：只保留 `stored_files`，状态分 pending 和 ready。服务端路径直接写入 S3；`temporary/` 前缀交给 S3 生命周期规则清理。

### G. 软删除（Phase 2，M，待做）

- **现状**：全仓库有 132 处 `deleted_at IS NULL` 谓词，但没有任何代码会把软删的行读回来。附带的后果：
  - 删掉的票据，图片永远不会被清理（`prune-storage.mjs:13`）。
  - 分类只做软删，所以专门写的 `ON DELETE SET NULL (category_id)` 外键从来没有触发过。
  - 分类改名时要用 `__cashier_internal_category_rename__` 临时名。
- **来历**：SQLite 同步时代（`9af391c0`）。
- **重写**：改为硬删除，外键级联；清理存量墓碑行属于破坏性操作，要单独审查。

### H. 前端（Phase 3，M–L，待做）

- **拦截未保存的离开**：`useLedgerHistorySync` 加上 `instrumentation-client` 里的 popstate 拦截，一共 14 个文件，通过 `history.go` 和 Next 的路由器对抗。连主题选择器都要显式保存。
- **设置区**：每个分区都有自己的保存/取消、脏状态和"服务端已被改动"检测。这套检测来自双人共享账本时代（`6a28a4f9`）。
- **单页 `?tab=`**：
  - 各 tab 的 URL 参数要加前缀区分，光这部分就有 394 行（`ledger-url-params.ts`）。
  - settings 需要的数据要穿过 6 层 props。
  - 还要靠 `ShellControllerProvider` 和 `useBookScopeStore` 两个变通方案，才能让外壳调用下层的状态。
- **hook 链**：73 个 hook 文件里有 54 个只有一个使用者。编辑一条记录要经过约 15 个 hook，mutation 链有 5 层。
- **读取路径**：`lib/queries` 用内联的 `typeof import()` 引用模块，绕过了"lib 不得依赖 modules"的检查。另外有两个读取仍然走 server action。
- **保留**：React Query、SSR 预取、专用读取路由、水位线轮询，都不改成 `revalidatePath`。

### I. 认证（Phase 3，M–L，待做）

- **next-auth 已经没有存在的理由**：OIDC 和 adapter 都已经删掉，现在只剩 3 个 Credentials provider 加 JWT。而且每个请求仍要查大约 4 次数据库，JWT 的无状态好处等于零。版本还锁在 beta。
- **尝试次数与锁定逻辑写了三份**：分别在 OTP、改邮箱、setup 里。
- **限流 key 有五种派生方式**：其中密码登录按邮箱限流时，直接用了原始邮箱当 key。
- **`API_KEY_PEPPER` 身兼四职**：凭证哈希、日志假名化、API 限流、密码按 IP 限流。
- **setup 模块**：约 680 行，是应用里唯一不需认证的写入口，而且会把明文 setup 码打进日志。建议改成本地命令，优先级低。
- **登录方式**：远期建议 passkey 为主、OTP 兜底，去掉密码。

### J. 测试与工具（持续进行，待做）

- **约 5k 行 mock 式单测**：它们 mock 掉被测的服务端代码，只断言调用参数，和真库集成测试重复。例如 `get-ledger-page-bootstrap.test.ts`，747 行里 mock 了 8 个模块。
- **测试目录还按已不存在的 `application/` 布局组织**：22 个文件，5,215 行。统计相关的测试散落在 5 个地方。
- **每个测试文件都跑一次完整迁移**：因为迁移锁表的压力，`maxWorkers` 被限制为 2。这很可能是 `check` 最慢的一环。
- **自制的架构检查器**：没有测试，而且锁住了 TypeScript 6（TS 7 移除了它依赖的 JS 编译器 API）。
- **scripts**：约 3.6k 行无类型 JS。数据种子写了三份（smoke、demo、测试 helper），存储 key 的约定也在 `prune-storage.mjs` 里重复了一遍。
- **CI 不拦部署**，而且每次推送要构建三次（CI、smoke、Vercel）。
- **文档**：中英文混用，部分描述与代码不符。

## 三、看起来重，但应该保留

- **金额存储**：`numeric(21,3)` 加 decimal.js。改成整数最小单位得不到任何好处。
- **AI 流程的租约与 fencing**：`after()` 会重叠执行，函数也可能中途被杀。
- **提交事务里先写持久记录，再调 `after()`**：Vercel 可能丢掉 `after()`。
- **按请求块做分类检查点**：大票据的分类一个函数跑不完。
- **"先锁账本、再锁文档"的加锁顺序**：用户自己的编辑会和后台写入竞争。`expectedVersion` 检查按 C 收窄到详情页整体保存。
- **前端数据层**：React Query、SSR 预取与注水、水位线轮询、专用读取路由。
- **API v1 凭证设计**：192 位随机值，HMAC 存储，绑定到分账。
- **Postgres 限流桶，以及防账号枚举、防时序攻击的措施**。
- **S3 直传加 sharp 归一化**：Vercel 请求体上限是 4.5MB，同时要剥离 EXIF。
- **工程底座**：严格的 tsconfig、testcontainers、MSW 网络守卫、smoke 测试、baseline 迁移守卫。
